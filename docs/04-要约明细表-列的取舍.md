# 要约明细表：列是怎么选的

界面在 `app.py` 的「要约明细」页，数据层在 `hkexdb/dealsview.py`，
落盘在 `data/deals.csv`（列定义是 `runner.DEAL_COLUMNS`，唯一真相源）。

---

## 表格里显示什么（12 列）

做港股 precedent transactions 时，一张可比表上真正会被引用的就这几样：

| 列 | 为什么在表里 |
|---|---|
| 公告日期 | T0。判断可比性的第一个筛子 |
| 代码 | 受要约方，港股五位代码，前导零要留住 |
| 受要约方 | 买的是谁 |
| **要约方** | 买方是谁。战略买家 / PE / 控股股东，估值逻辑完全不同 |
| 类型 | MGO / VGO / PO。这三类不能混在一张可比表里 |
| 对价形式 | 现金 / 证券 / 混合。证券对价的溢价口径要另算 |
| 要约价 | 每股 |
| 溢价率 | 主值 |
| **溢价口径** | 见下，这一列不许拿掉 |
| 交易规模 | 要约项下最高现金代价（as printed） |
| **要约方FA** | 谁做的。找 comp 时也是在找「谁做过这类单」 |
| 置信度 | 低的整行标黄，必须人看过才能用 |

### 为什么「溢价口径」必须紧挨着溢价率

一个 `-15.45%` 不写明是「未受干扰日前 30 日均价」，放进可比表就是污染 ——
隔壁那单可能用的是最后交易日收市价。3336 这两个口径差 2.05 个百分点。

所以 `DEAL_COLUMNS` 里「主值口径」永远排在「主值溢价率」的下一位，
`test_premium_basis_sits_next_to_the_premium_number` 守着这个相邻关系。

## 明细面板里额外显示什么

点一行，下面显示这一单的全部字段，分四组：

1. **当事方** — 加上受要约方全称、要约方 FA
2. **交易条款** — 加上上市地位意向（拟维持 / 拟撤销）、停牌前最后交易日
3. **溢价／折让梯子** — 公告里印的**每一条**比较，主值那条标 `←主值`
4. **复核** — 置信度、V3–V8 复算结果、备注
5. **原文出处** — 每个字段第几页、原话是什么（铁律三）

### 为什么梯子要整条列出来

主值只是「我们按 selectors.py 的规则选的那一条」。下一个用这张表的人
可能要按最后交易日收市价重排，只给主值等于把选择权拿走了。

固定列覆盖 12 个常见口径，公告用了别的口径就落进「其他比较项」——
1417 的「規則3.7 公告前收市價」和 3336 的「前180日均价」当初就是
因为没有兜底列而无声消失的。`test_no_comparison_is_silently_dropped_from_the_table`
守着它。

## 还没有的列（留空，不编）

这几样投行也会看，但目前抽不出来，所以**表里没有**，而不是填个看起来
合理的数：

- **要约前后持股比例** —— 是否触发 30% 强制点。措辞变体太多，
  抽错会得到一个看着正常的错数字，比抽不到危险。
- **最低接纳条件 / 先决条件** —— 同上，条件条款是长段落，标题层和
  正则都不够。
- **隐含 100% 股权价值、EV** —— 公告里通常不印，算出来就违反铁律一。
- **交易状态（进行中 / 完成 / 失效）** —— 要跟踪后续公告才知道，
  是下一阶段的事。

---

## 两条路径必须长成同一张表

「刚跑完」用内存里的 `Deal`，「第二天打开」从 `deals.csv` 读。
这两条路各长一套字段名是界面最容易出的 bug：跑完好好的，重开一片空白。
`rows_from_deals` 和 `load_rows` 共用 `DEAL_COLUMNS`，
`test_csv_and_memory_produce_the_same_shape` 逐字段比对。

出处存在 `data/deals_evidence.json`（按 PDF 链接索引）——
CSV 塞不下整段引文，而重启后没有出处就等于违背铁律三。
