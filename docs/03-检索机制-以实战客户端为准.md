# 检索机制：以 hkex_client.py 为准

`hkexdb/listing.py` 的检索逻辑**照搬自你提供的 `hkex_client.py`**（实战验证过）。
我原先那版是按接口结构推测写的，有五处硬错误。逐条记下来，防止有人改回去。

## 我错在哪

| 项目 | 我原来写的（错） | 实战客户端（对） | 后果 |
| --- | --- | --- | --- |
| **翻页机制** | `pageNo` 递增 | **`rowRange` 递增后重查，按 `NEWS_ID` 去重** | 接口没有 `pageNo`，参数被忽略，每轮返回同一批 |
| **切块粒度** | 按月 | **按天** | 按月会撞服务端 10000 条上限并**静默截断** |
| `searchType` | `1` | `0` | 日期区间全量检索用 0；1 是类别检索 |
| `t1code`/`t2Gcode`/`t2code` | `-1` | **`-2`** | 取值不对 |
| `lang` | `ZH` | `zh`（小写） | |
| 检索策略 | 标题关键词 | **不带关键词，抓全量** | 关键词漏一个变体就静默漏一单 |
| 会话 | 直接打接口 | **先访问检索页** | 接口依赖检索页种的 cookie |

## 翻页机制：为什么必须按 NEWS_ID 去重

披露易这个接口**没有 pageNo**。`rowRange` 是「返回前 N 条」的上限，
要拿更多就把 N 调大重查一次 —— 每次返回的都是**从头开始的一整段**：

```
rowRange=100 → 前 100 条
rowRange=200 → 前 200 条（前 100 条与上一轮完全重复）
rowRange=300 → 前 300 条
```

250 条记录不去重的话会存成 100+200+250 = **550 条**。
测试 `test_overlapping_rounds_are_deduplicated_by_news_id` 把这个数字钉死了。

## 为什么按天切

服务端单次查询返回上限约 **10000 条**（`SERVER_RECORD_CAP`），
超过之后加大 `rowRange` 也没用，只能缩小日期区间。

单日全市场公告约 600~800 条，安全余量很大。
按月切是 30 × 700 ≈ 21000 条，**必然超限，而且是静默截断**——
你不会收到任何错误，只会少数据。
`fetch_day` 在 `loadedRecord >= 10000` 时会打警告。

## 为什么不用标题关键词

抓全量 + 本地筛，比带关键词检索强在一点：

**词表改了只要重跑 screening，不用重抓。**

关键词检索一旦漏了变体（比如「恢復股份買賣」vs「恢復買賣」），
那一单从抓取阶段就没了，后面所有质控层都救不回来 ——
手册第一节说的「源头漏检是四层质控都救不回来的错」正是这个意思。

一年约 20 万条记录，本地筛毫无压力。

## HTML 清洗：不做的话词表会静默失配

接口返回的 `TITLE` 是 HTML 片段，带实体和 tooltip 残留：

```
寄發綜合文件 &amp; 接納表格
每月最新資料<div class='tip'>提示</div>
要約&#x2f;收購
```

不还原的话，标题看着对，但拿去和词表比就是不等 —— **静默失配**。

处理方式遵循「原始层不动，加工层另开」：
raw 表同时保留 `TITLE`（原样）和 `TITLE_CLEAN`（清洗后），
screening 读 `TITLE_CLEAN`，两份都在，可随时回溯。

## 类别交叉核对（双保险）

`fetch_category_crosscheck()` 实现了实战客户端的 `search_by_category`：
`searchType=1, t1code=10000, t2code=<类别代码>`，按月分段。

**这一路不能单独用作抓取口径** —— 分类是发行人自己选的，归错类会静默漏掉。
它的用途是和全量口径**比差集**：差集里的东西告诉你词表还缺什么变体、
或者归类有多不可靠。

`config.yaml` 的 `category_t2codes` 现在是空的，等确认收购相关类别代码后填。

以下能力在 `hkex_client.py` 里有，本项目暂未纳入，需要时再补：

## 按代码检索：第 2 层质控的前提

手册把「公司级完备性对账」标为四层里**最强的一层** ——
每家公司的 T0 必须落在「主清单／窗口前／特殊品种／流产案」四选一，数量守恒。

要做这个对账，就得能按公司把它的全部历史公告拉出来，
而按代码检索必须先把 `0700` 换成披露易内部的 `stockId`。
**上一轮我完全漏掉了这块，等于第 2 层质控根本做不了。**

```bash
python run_ticker.py 1417 3336 00195
```

产出 `data/ticker/<代码>.csv`。首次运行会下载两份证券清单并缓存到
`data/stock_id_map.json`。

**已除牌清单必须要**：被要约收购成功的公司往往随后就退市了，
只查活跃清单会漏掉一大批先例交易。

## 我在客户端里发现的一处latent 脆弱

`_load_stock_id_map` 靠**字典插入顺序**实现「活跃证券优先」：

```python
_STOCK_LIST_URLS = {"inactive": ..., "active": ...}   # inactive 在前
...
mapping[code] = (item.get("i"), category)             # 后写覆盖先写
```

能跑，但依赖 `_STOCK_LIST_URLS` 那两行的字面顺序。
谁把它们调换一下，优先级就**静默反过来**，而且不报错 ——
表现是活跃证券被打上 `category=1`，按代码检索时查不到。

本项目改成显式判断：已登记的活跃记录不被已除牌记录覆盖，
不依赖任何顺序。测试
`test_active_listing_wins_over_delisted_regardless_of_load_order` 守着它。

**顺带一提**，写这条测试时我自己踩了同一类坑：
判断 URL 用了 `"activestock" in url`，而 `inactivestock` 里也含 `activestock`，
两个 URL 被判成同一个。和 screening 的坑②是同一类子串陷阱。

## PDF 下载：我原来用的是裸会话

客户端的 `download_pdf` 用 `self.session` —— **和检索共用一个会话**，
带着检索页种下的 cookie。

我原来的 `pdf_source.fetch_bytes` 是 `session or requests.Session()`，
默认新建一个裸会话。在需要 cookie 的路径上会拿不到文件，
而表现可能只是一个 403 或一段 HTML —— 又是静默失败。

现在 `run_pdf.py` 传入建立好会话的 session；没传时会打警告。
`full_url()` 让你可以直接粘 raw 表里的 `FILE_LINK` 相对路径。

## 并发：为什么必须共享限速器

`run(max_workers=N)` 按天切成 N 个**连续段**并发抓，
但所有线程**共享一个 `RateLimiter`** —— 总请求频率与单线程完全一致。

并发的目的是让网络延迟重叠，不是提高对服务器的请求频率。
每个线程各自限速等于把总频率乘以 N，那是对方会讨厌的行为。

并发还带来两个必须处理的点：

- **checkpoint 是「读-改-写」**，不加锁会丢记录 —— 丢了就静默少一天数据。
  `RawStore` 现在有锁，且 checkpoint 用临时文件 + 原子改名写入。
- **HTTP 缓存写入**同样改成临时文件 + 原子改名，中断不留半截 JSON。

## 取消与进度

GUI 的「运行」按钮需要能停。`cancel_event`（`threading.Event`）置位后，
长任务在每一轮请求前检查并抛 `listing.Cancelled`。

**中途取消的那一天不会被标记完成** —— 否则重跑会跳过它，静默少数据。
测试 `test_cancel_midway_leaves_the_day_unfinished` 守着这条。

`progress_cb(已完成天数, 总天数, 累计条数)` 每完成一天调一次。
回调是外部代码，抛异常不会拖垮抓取（客户端也是这么做的）。

## 一处改进：活跃证券优先不该靠字典顺序

实战客户端里 `_STOCK_LIST_URLS` 是个字典，先读 `inactive` 再读 `active`，
靠**后写覆盖先写**实现「活跃证券优先」。能跑，但依赖字面书写顺序：
谁把那两行调换一下，优先级就静默反过来，不报错，只是已除牌的
`category=1` 会被用到活跃证券上，检索结果随之出错。

本项目改成显式判断：已登记的活跃记录不被已除牌记录覆盖，
顺序怎么写都不影响结果。

## 一处修正：PDF 下载必须复用已建立会话的 session

实战客户端的 `download_pdf` 用的是 `self.session` —— 和检索**共用一个**，
带着检索页种下的 cookie。

我第一轮写的 `pdf_source.open_pdf` 新建了一个裸 `requests.Session`，
没有那些 cookie。现在改成接收外部传入的 session，未传时打警告。

## 一处优化：`row_range_step` 从 100 改到 1000

你指出翻页会把之前的记录再拉一遍，流量是平方级增长。实测单日 700 条：

| 步长 | 请求轮数 | 累计拉回 | 浪费 |
| --- | --- | --- | --- |
| 100 | 7 | 2800 条 | 4.0 倍 |
| 500 | 2 | 1200 条 | 1.7 倍 |
| **1000** | **1** | **700 条** | **无** |

单日全市场约 600~800 条，取 1000 则绝大多数日子一轮取完。
219 天的话请求数从约 1500 次降到 219 次，耗时从约 38 分钟降到约 6 分钟。
超过 1000 条的日子会自动加到 2000 再取一次，仍然正确。

## 并发的正确用法

```bash
# config.yaml 不控制并发，由入口参数控制
python run_listing.py            # 单线程
```

`listing.run(cfg, max_workers=4)` 把日期切成 4 个连续段并行跑，
**四个线程共用一个 `RateLimiter`** —— 并发的目的是让网络延迟重叠，
不是提高对服务器的请求频率。每线程各自限速等于把总频率乘以线程数，
那是对方会讨厌的行为。

# 界面：一屏看完所有公告数据

```bash
python run_report.py
```

产出 `data/screening/report.html` —— **单个自包含文件**，
无外链无 CDN，双击打开，断网可用（实测 16 KB）。

- 顶部卡片按判定桶分组，**点击即筛选**；人工复核桶排最前
- 搜索框可搜代码／名称／标题／判定依据
- 点表头排序，点行展开**判定依据**（铁律三要的可追溯）
- 深浅色自适应

一个安全细节：数据以 JSON 嵌在 `<script>` 里，公告标题若含 `</script>`
会提前闭合脚本标签造成注入。`_safe_json` 把 `< > &` 转义成 `\uXXXX`，
数据本身一字不差。回归测试
`test_embedded_data_cannot_break_out_of_the_script_tag` 守着它。

# 递进逻辑：每一步知道前置做完没有

```bash
python run_status.py
```

各步之间有严格先后依赖，前一步没做完就跑下一步，
拿到的往往不是报错而是「0 条」或空报告 —— 又是静默失败。
`pipeline.status()` 把依赖显式化：

```
[!] 1. 勘察接口       未运行
[!] 2. 抓取列表       未运行
[OK] 3. 质控筛查      已筛 15 行
[OK] 4. 生成网页      已生成 …/report.html
[!] 5. 读公告原文     按需运行，不计完成状态
下一步：python run_probe.py
```

两个判定细节：

- **勘察报告存在 ≠ 勘察完成**。顶部带「本次勘察无效」横幅的（一个请求都没
  发出去）不算完成，否则流水线会指着第 2 步说可以走了，而参数一个都没验证过。
- **抓了一部分天数不算完成**。checkpoint 里的天数少于日期范围就显示
  `已完成 N/M 天`，防止带着缺口往下走。

每个入口脚本跑完都会打印这张状态表。
