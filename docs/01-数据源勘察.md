## 问题 1：检索机制

### 1.1 URL 结构 🟡

| 用途 | 地址 |
| --- | --- |
| 检索页（人看的） | `https://www1.hkexnews.hk/search/titlesearch.xhtml?lang=zh` |
| 结果接口（程序用的） | `https://www1.hkexnews.hk/search/titleSearchServlet.do` |

`lang` 取 `zh` / `en`，决定返回中文版还是英文版公告。

### 1.2 静态 HTML 还是 JS 动态渲染？ 🟡

判断：**页面是服务端渲染的外壳，结果由 JS 异步取回**。
`.xhtml` 后缀说明是 JSF 技术栈，这类页面的搜索结果通常走 AJAX。

**这一点对做法影响很大**，所以 `run_probe.py` 会实测：
它数首屏 HTML 里有多少个 `.pdf` 链接。

- 首屏有 PDF 链接 → 结果是服务端渲染的，可以直接解析 HTML
- 首屏没有 → 必须调接口（本项目按这个假设写的）

### 1.3 有无可用接口 🟡

有。`titleSearchServlet.do` 返回 JSON，比解析 HTML 稳定得多。

**已知的坑：`result` 字段是「JSON 字符串套 JSON」**——
即 `result` 的值是一个字符串，字符串的内容才是记录数组，要解析两次。
`listing._parse_payload()` 两种情况都兼容了，并有测试覆盖。

推测的请求参数：

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| `fromDate` / `toDate` | `YYYYMMDD` | 🟡 也可能叫 `from` / `to`，probe 会两套都试 |
| `title` | 关键词 | 标题模糊匹配 |
| `lang` | `ZH` / `EN` | 注意这里是大写，和检索页 URL 的小写不同 |
| `rowRange` | 每页条数 | |
| `pageNo` | 页码，从 1 起 | |
| `t1code` / `t2Gcode` / `t2code` | 分类代码 | `-1` = 不限，见问题 2 |
| `market` | `SEHK` | |
| `category` / `documentType` / `stockId` / `searchType` | | 🟡 含义未完全确认 |

响应顶层含 `hasNextRow`（还有没有下一页）、`recordCnt`、`result`。
单条记录的字段 🟡：`NEWS_ID`、`DATE_TIME`、`STOCK_CODE`、`STOCK_NAME`、
`TITLE`、`LONG_TEXT`、`FILE_LINK`、`FILE_INFO`、`FILE_TYPE`。
`FILE_LINK` 是相对路径，要拼上 `https://www1.hkexnews.hk`。

## 问题 2：Headline Category 能否直接按类别过滤？

### 2.1 存不存在收购/要约相关分类？ 🔴 **我不知道**

我的印象是分类体系分两层（`t1code` 一级、`t2code` 二级），
一级里有「公告及通告」，二级里有收购合并相关项。
**但具体代码值我不知道，也不会编一个给你**——
编错的后果不是报错，是静默漏抓，而漏抓你不会发现。

`probe.py` 用三条路子去问：

1. 抓检索页，把所有 `<select>` 下拉框的 `option` 全部导出
   （下拉框就是官方分类清单的第一手来源）
2. 试几个可能的分类 JSON 地址
3. 在拿到的 JSON 里递归搜「收購 / 要約 / 合併 / takeover / privatisation」等字样，
   把命中节点的代码打出来

三条都没结果的话，报告里会给你一个三分钟的手工步骤
（F12 → Network → 勾一个类别 → 看请求参数怎么变）。

### 2.2 ⚠️ 就算找到了分类代码，也不要只靠它过滤

这是我要特别提醒的一点，和铁律二直接相关。

**分类是发行人自己选的，不是交易所审定的。** 同一类交易，不同发行人
可能归到不同类别，也可能归错。只按类别过滤，漏掉的公告在你的数据库里
表现为「这单交易不存在」——**这是静默污染，比报错危险得多**。

所以阶段一的抓取口径应当这样定：

1. 按标题关键词抓一遍（recall 优先，就是 config.yaml 现在的默认配置）
2. probe 确认分类代码后，再按类别抓一遍
3. **比对两边的差集**：
   - 类别有、关键词没有 → 说明关键词不够，补关键词
   - 关键词有、类别没有 → 说明存在归类不一致，**必须两种口径并用**
4. 差集稳定后，才把最终口径固定下来

第 3 步的比对我建议放到阶段一的验收里做。

## 问题 2 附：建议的请求频率 🟢（这是判断，不是事实）

配置在 `config.yaml` 的 `http.min_interval_seconds`，默认 **1.5 秒/次**
（约 40 次/分钟），单线程、不并发。

理由：

- 这是一个公开披露平台，抓取公开信息本身是其设计用途之一
- 但它是市场基础设施，任何影响可用性的行为都不可接受，所以宁慢勿快
- 你的数据量不大：一年的公告列表，切成 12 个月块 × 3 个查询 × 几页，
  几百次请求就够了。按 1.5 秒算也就十几分钟，没必要压榨速度
- **加上缓存后，重跑几乎不发请求**，所以慢一点的代价只付一次

三条硬规则：

1. `run_probe.py` 会读 `robots.txt`。**若声明了 `Crawl-delay`，
   把 `min_interval_seconds` 调到不低于该值**，这不是建议是要求。
2. UA 里填你的真实邮箱（`config.yaml` 里现在是 `YOUR_EMAIL_HERE` 占位符）。
   对方要是觉得你请求太频，能直接联系你，而不是直接封 IP。
3. 不要加并发。真要提速，先把 `chunk_months` 调大减少请求数，
   而不是调小 `min_interval_seconds`。
